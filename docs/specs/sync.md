# Lists: данные и синхронизация

Состояние: реализовано в ядре и проверено тестами; запуск по расписанию (S15) реализован в приложениях и проверен только вручную; запуск после правки на Android проверен на эмуляторе для случая «процесс убит сразу после сохранения», случай «нет сети» не проверялся; слежение за папкой в приложении для macOS собрано, но в работе не проверялось. Источники: запрос автора проекта от 2026-10-05; решения в [architecture.md](../architecture.md).

## Назначение и границы

Документ описывает, как устроены данные на устройстве, как сливаются правки и что лежит в удалённом хранилище. Сервера у проекта нет: хранилище — каталог WebDAV или локальная папка, от которых требуется только читать, писать, перечислять и удалять файлы.

Не входит: шифрование содержимого на стороне клиента, совместный доступ нескольких людей, мгновенная доставка (хранилище не умеет уведомлять).

## Модель

Сущности: `list`, `task`, `attachment`. Идентификатор — UUID версии 7, создаётся на устройстве.

Каждое поле сущности хранится отдельной строкой: вид, идентификатор, имя поля, значение в JSON, метка времени. Таблицы `lists`, `tasks`, `task_tags`, `attachments`, по которым работают запросы интерфейса, выводятся из этих строк и пересобираются для сущности при каждом изменении её полей.

Поля задачи: `list`, `parent`, `title`, `notes`, `start`, `due`, `priority`, `repeat`, `remind`, `pos`, `done`, `deleted`, `log_of`, а также по одному полю `tag:<имя>` на тег со значением `true` или `false`.
Поля списка: `name`, `color`, `icon`, `sort`, `show_done`, `default_priority`, `default_due`, `pos`, `archived`, `deleted`.
Поля вложения: `task`, `name`, `mime`, `size`, `sha256`, `deleted`.

Даты — строки `ГГГГ-ММ-ДД` или `ГГГГ-ММ-ДДTЧЧ:ММ` без часового пояса.

## Требования

### Слияние

- S1. Метка времени — гибридные логические часы: миллисекунды, счётчик, идентификатор устройства, записанные строкой фиксированной ширины, так что строки сравниваются как метки. Получив чужую метку из будущего, устройство продвигает собственные часы за неё.
- S2. Для каждой тройки «вид, идентификатор, поле» побеждает значение с большей меткой. Применение изменения идемпотентно, результат не зависит от порядка применения.
- S3. Удаление — поле `deleted`, а не стирание строк. Удалённая на одном устройстве и отредактированная на другом задача остаётся удалённой, но правка сохраняется и видна после восстановления.
- S25. Удаление навсегда — очистка корзины и очистка «Выполненных» — тоже поле: `purged`. Оно сливается по S2, поэтому очищенное на одном устройстве исчезает на остальных. Обратной операции нет: задача, которую одно устройство очистило, а другое без связи вернуло в работу или восстановило из корзины, остаётся удалённой. Подзадачи очищенной задачи скрыты вместе с ней.
- S4. Порядок внутри списка и внутри родителя задаёт поле `pos` — строка, между любыми двумя значениями которой можно построить третье. При равных `pos` порядок определяется идентификатором.
- S5. Если после слияния цепочка родителей образует цикл, каждое устройство одинаково его разрывает: у задачи из цикла, чьё поле `parent` имеет наибольшую метку, родитель считается пустым. При слиянии хранимые поля не переписываются; разрыв записывается в поле при следующем локальном перемещении любой задачи, чтобы подавленный родитель не «ожил» после него.
- S6. Задача, чей список удалён или неизвестен, показывается во «Входящих».
- S7. Запись о завершённом повторе получает идентификатор, вычисленный из идентификатора задачи и срока повтора. Два устройства, завершившие один и тот же повтор без связи, создают одну запись, а не две.

### Удалённое хранилище

```
lists/v1/
  vault.json                    {"format":1,"vault":"<uuid>"}
  log/<устройство>-<номер>.jsonl
  log/<устройство>-<номер>.snap   пустой файл: у устройства есть снимок с этим номером
  snap/<устройство>-<номер>.jsonl
  blobs/<первые два знака>/<sha256>
  push/<устройство>.json        {"v":1,"url":"https://…"}
```

- S8. Файл `log/…` неизменяем и принадлежит одному устройству; номера идут подряд с единицы. Первая строка — заголовок с версией, устройством, номером и числом изменений, дальше по изменению на строку. Файл с неверным числом строк или нечитаемой строкой считается недописанным: устройство не продвигается за него и повторяет чтение при следующей синхронизации.
- S9. Устройство помнит для каждого другого устройства номер последнего прочитанного файла. Синхронизация: запрос списка `log/`, чтение новых файлов, выгрузка собственных изменений новым файлом. Содержимое файла фиксируется локально до первой попытки выгрузки, поэтому повтор после сбоя отправляет те же байты под тем же номером.
- S10. Когда собственных файлов журнала становится больше 64, устройство записывает `snap/<устройство>-<номер>.jsonl`: полное состояние по номер своего журнала включительно и таблицу «устройство → номер последнего учтённого файла». После успешной записи оно кладёт в `log/` отметку `<устройство>-<номер>.snap`, затем удаляет свои покрытые файлы журнала, прежний снимок и прежнюю отметку.
- S11. Если файла со следующим номером у какого-то устройства нет, а его снимок новее прочитанного, читается снимок. О снимке читатель узнаёт из отметки в `log/`; после слияния счётчики всех устройств поднимаются до значений из его таблицы. Слияние снимка подчиняется S2, поэтому читать его безопасно в любой момент.
- S12. Устройство, впервые подключённое к непустому хранилищу, читает журналы и снимки остальных, затем выгружает собственное состояние. Локальные данные не стираются. При смене хранилища нумерация собственного журнала продолжается, а первая синхронизация публикует снимок: без него читатели нового хранилища не нашли бы файл с номером один.
- S13. Вложение выгружается в `blobs/` по хешу содержимого, если его там нет, и скачивается при первом обращении либо в фоне. Изменения полей не ждут вложений.
- S14. `vault.json` с неизвестным номером формата останавливает синхронизацию с понятной ошибкой; локальная работа продолжается. Файл читается при первой синхронизации с хранилищем после запуска приложения и ещё раз, когда встретился файл журнала или снимок, который не удалось прочитать.
- S17. Синхронизация, которой нечего читать и нечего выгружать, стоит одного запроса — списка `log/`. Список `snap/` запрашивается при первой синхронизации с хранилищем после запуска приложения и когда отметки не объясняют пропуск: у устройства нет следующего файла, но есть более поздние, либо от уже известного устройства в `log/` не осталось ничего. Так читаются снимки, записанные версиями без отметок.

### Когда запускается

- S15. После локальной правки — через две секунды тишины; на Android этот запуск отдан системе, поэтому он состоится, даже если приложение к тому времени закрыто, а без сети дождётся её появления. При выходе приложения на передний план. Пока приложение активно — раз в минуту. На Android дополнительно фоновой задачей раз в 15 минут при наличии сети. При синхронизации через папку приложение для macOS и веб-сервер запускают её ещё и тогда, когда в `log/` этой папки появился или исчез файл: так доходят правки, которые принесла в папку другая программа (Syncthing, iCloud Drive).
- S16. Сбой сети не теряет данных: несинхронизированные изменения остаются локально и уходят при следующей попытке.

### Толчок между устройствами

Хранилище уведомлять не умеет, поэтому чужая правка ждёт следующего запуска по S15. Толчок сокращает ожидание: устройство, выгрузившее изменения, просит остальные синхронизироваться. Данных толчок не несёт, они по-прежнему идут через хранилище. Состояние: ядро проверено тестами, включая ожидание толчка, на которое опираются веб-сервер и приложение для macOS; сами циклы приёма в веб-сервере и в приложении для macOS собраны, но в работе не проверялись; приём на Android проверен на эмуляторе с приложением ntfy 1.25.2 в роли распространителя (2026-10-06): задача, добавленная на другом устройстве, дошла до телефона с убитым процессом приложения примерно за три секунды.

- S18. Устройство, которому приложение назначило адрес приёма, публикует его в `push/<устройство>.json`. Файл переписывается, когда адрес меняется, и удаляется, когда приём выключен. Адрес — только `http://` или `https://`.
- S19. После синхронизации, которая выгрузила изменения или вложения, устройство читает `push/` и отправляет по каждому чужому адресу `POST` с телом `sync`. Синхронизация, которой нечего выгружать, `push/` не читает и ничего не отправляет.
- S20. Толчок не обязателен к доставке: ошибка или молчание адресата на результат синхронизации не влияют, ожидание ответа ограничено пятью секундами. Запуски по S15 остаются.
- S21. Получив толчок, приложение запускает обычную синхронизацию. Она ничего не выгружает, поэтому ответного толчка нет.
- S22. Приложение для macOS и веб-сервер принимают толчки через сервер [ntfy](https://ntfy.sh), общий или свой: в настройках задаётся его адрес. Устройство один раз выбирает случайную тему из 32 шестнадцатеричных знаков, публикует `<сервер>/<тема>` как свой адрес приёма и, пока работает, держит подписку на эту тему. Имя темы — единственная защита: сервер видит моменты правок, но не данные.
- S23. Подписка, оборвавшаяся после того как была установлена, считается толчком: за время разрыва сообщение могло пройти мимо. Неудачная попытка подключиться повторяется не чаще раза в десять секунд.
- S24. Приложение для Android принимает толчки через [UnifiedPush](https://unifiedpush.org): соединение с сервером держит приложение-распространитель, установленное на устройстве (например, ntfy), оно же выдаёт адрес приёма. Приём включается в настройках синхронизации; без распространителя включить его нельзя, и приложение об этом говорит. Получив толчок, приложение ставит синхронизацию срочной задачей системы, поэтому она идёт и при закрытом приложении. Фоновая синхронизация раз в 15 минут остаётся.

## Инварианты

- Два устройства, получившие одинаковый набор изменений в любом порядке, показывают одинаковые данные.
- В хранилище нет файла, который пишут два устройства, кроме `vault.json`, создаваемого один раз, и содержимого `blobs/`, где имя определяет содержимое.
- Формат файлов версионируется номером в `vault.json` и в заголовке каждого файла.

## Известные ограничения

- Устройство с часами, ушедшими далеко вперёд, выигрывает конфликты за одно и то же поле, пока остальные не увидят его метки и не продвинут свои часы.
- Строки удалённых записей остаются в базе и в снимках.
- Журнал устройства, которое больше не появится, остаётся в хранилище, пока его не удалят вручную.
- Содержимое в хранилище не зашифровано.
- Адрес приёма толчков лежит в хранилище открыто, и устройства шлют `POST` по любому адресу оттуда. Тот, кто может писать в хранилище, может заставить их обратиться к произвольному адресу; данных такой запрос не несёт.
- Сервер ntfy, требующий входа, не поддерживается: подписка и отправка идут без учётных данных.
- Запись в `push/` устройства, которое больше не появится, остаётся, пока её не удалят вручную; толчки по ней уходят впустую.
- Устройство с версией без отметок (до S17), которое ни разу не встречалось читателю и сжало весь свой журнал, читатель увидит после перезапуска приложения или после следующей правки на том устройстве.

## Проверочные сценарии

Тесты — в `core/tests/sync.rs`, хранилищем служит временная папка; обмен по HTTP проверяет `core/tests/webdav.rs` против локального WebDAV-сервера из `core/tests/common/dav.rs`. Тест `devices_converge_whatever_the_order_of_edits_and_syncs` прогоняет три устройства через случайные правки и синхронизации и сверяет итог.

- S2: устройство A меняет название, B меняет срок той же задачи без связи → после синхронизации обоих у задачи новое название и новый срок на обоих устройствах.
- S2: A и B меняют название одной задачи → у обоих название с большей меткой; повторная синхронизация ничего не меняет.
- S3: A удаляет задачу, B меняет её заметку → задача удалена у обоих; после восстановления заметка — от B.
- S25: на A завершены три задачи в разные дни, B их видит → A очищает завершённое раньше заданного дня → у обоих в «Выполненных» одни и те же оставшиеся задачи. B возвращает очищенную задачу в работу, не зная об очистке → после синхронизации её нет у обоих.
- S5: A переносит X под Y, B переносит Y под X → у обоих одинаковое дерево без цикла.
- S7: A и B завершают один повтор → в «Выполненных» одна запись.
- S8: файл журнала обрезан на середине → чтение останавливается на нём; после замены целым файлом изменения применяются.
- S10, S11: A создаёт больше 64 файлов и сжимает журнал → новое устройство C получает полное состояние; устройство B, отставшее до сжатия, догоняет через снимок.
- S17 (в `core/tests/webdav.rs`): синхронизация без правок — один запрос; отставшее устройство догоняет через снимок, не запрашивая список `snap/`; снимок без отметки находится по списку `snap/`.
- S14: формат хранилища вырос, пока приложение работало → первый же нечитаемый файл останавливает синхронизацию с той же ошибкой.
- S15, папка: в `log/` появился файл другого устройства → `folder_changed` один раз отвечает «да»; после синхронизации и без новых файлов — «нет».
- S18–S20 (в `core/tests/push.rs`): A и B публикуют адреса → правка на A даёт один `POST` на адрес B и ни одного на адрес A; синхронизация без правок не даёт ни одного; выключенный приём убирает запись; недоступный адрес не мешает синхронизации.
- S22, S23 (в `core/tests/push.rs`, сервер ntfy изображает тест): правка на A будит ожидание на B, после синхронизации у B задача A; обрыв подписки будит ожидание; без адреса сервера ожидание возвращается ни с чем.
- S12: C с собственными задачами подключается к хранилищу A → у обоих объединение задач.
- S13: A прикрепляет файл → после синхронизации B получает запись о вложении, затем содержимое с тем же хешем.
