## Purpose and scope

This document describes how the data is laid out on a device, how edits are merged and what lies in the remote storage. The project has no server: the storage is a WebDAV directory or a local folder, and all it has to do is read, write, list, move and delete files.

Out of scope: encryption of a CalDAV storage (S54), turning encryption off and encrypting the data folder on the device, shared access for several people, instant delivery (the storage cannot send notifications).

## Model

Entities: `list`, `task`, `attachment`, `settings`. The identifier is a UUID version 7, created on the device.

Each field of an entity is stored as a separate row: kind, identifier, field name, value in JSON, timestamp. The tables `lists`, `tasks`, `task_tags`, `attachments`, which the queries of the interface use, are derived from these rows and rebuilt for an entity on every change of its fields.

Task fields: `list`, `parent`, `title`, `notes`, `start`, `due`, `priority`, `repeat`, `remind`, `pos`, `done`, `wont`, `deleted`, `project`, `log_of`, and one field `tag:<name>` per tag with the value `true` or `false`. The tag field fits the key limit: the prefix `tag:` and the name together are no longer than 200 bytes (S51).
List fields: `name`, `color`, `icon`, `sort`, `show_done`, `default_priority`, `default_due`, `pos`, `archived`, `deleted`.
Attachment fields: `task`, `name`, `mime`, `size`, `sha256`, `deleted`.
Settings fields: `keep_done`. There is one entity, with the identifier `app`.
The `blob` field: `gone` — the content with this hash is deleted from the storage (S48). The identifier is the SHA-256 of the content, not a UUID.

Dates are strings `YYYY-MM-DD` or `YYYY-MM-DDTHH:MM` without a time zone.

## Requirements

### Merge

- S1. A timestamp is a hybrid logical clock: milliseconds, a counter and the device identifier, written as a fixed-width string, so that the strings compare as timestamps. A device that receives a foreign timestamp from the future moves its own clock past it.
- S2. For each triple "kind, identifier, field" the value with the greater timestamp wins. Applying a change is idempotent, and the result does not depend on the order of application.
- S51. A register key — kind, identifier and field name — is non-empty and no longer than 200 bytes of UTF-8; a change with any other key is not applied. A tag is stored as the field `tag:<name>`, and a tag name is one word, so together with the prefix it fits the same 200 bytes: the longest name is 196 bytes (196 Latin letters or 98 Cyrillic ones). The local APIs do not write a field that would fail this check: `add_tag` and quick entry refuse with a message about the limit, import skips the tag and gives their number in the report (I10 in [import.md](import.md)), CalDAV neither reads nor writes the category (C31 in [caldav.md](caldav.md)). A tag over the limit written by a version before this rule is not shown on the device and is not copied into a repeat record or a duplicate; on merge and on restoring a backup its field is not applied, so other devices do not have the tag. The storage format number (S14) does not change: a version with the previous limit accepts the fields this version creates.
- S52. Attachment content is transferred as a stream: the upload reads the file from disk, the download writes into a temporary file and computes the SHA-256 on the way. Memory does not grow with the file size, and the fallback move path of S49, when the storage cannot do `MOVE`, goes through a temporary file in the system folder. The per-file limit (R140 in [product.md](product.md)) applies to downloads as well: content over the limit is not saved, the attachment keeps waiting, and the error names the limit. A temporary file whose hash does not match the name is deleted; every download has its own temporary file name, so a pass and a request (S35) do not get in each other's way.
- S53. Android: saving the sync settings with a chosen side (S36) runs to the end even if the settings window was closed while it was running (#320). The password and the push token are written before the device data is erased (S37) or remembered for sending (S38); if the storage could not be saved, the previous password and token are restored. After saving, sync starts. While one save is running, a second one does not start, and the app says so.
- S3. Deletion is the `deleted` field, not erasing rows. A task deleted on one device and edited on another stays deleted, but the edit is kept and is visible after restoring.
- S25. Deleting for good — emptying the Trash and clearing "Completed" — is also a field: `purged`. It merges by S2, so what is cleared on one device disappears on the others. There is no reverse operation: a task that one device cleared and another, while offline, reopened or restored from the Trash stays deleted. The subtasks of a cleared task are hidden together with it.
- S32. Settings shared by all devices are the `settings` entity with the fixed identifier `app`; its fields merge by S2 like any others. There are three fields. `inbox_hidden` — whether "Inbox" is hidden (R121 in [product.md](product.md)): `true` or `false`, without the field — `false`. `new_task_list` — the default list for new tasks (R40): the string `"inbox"`, `"last"` (the last used one) or a list identifier; without the field or with any other value — `"inbox"`. Which list was the last used one is not written to the storage. `keep_done` — how long a completed task stays in the view (R68 in [product.md](product.md)). The value is a number of minutes (0 — "at once", more than 1440 reads as 1440) or a string: a number of seconds with the letter `s` (`"5s"`, `"15s"`; more than a day reads as a day) or `"day"` — until the end of the day. A whole number of minutes is written as a number, so that a version that knows only minutes understands it. While the field is absent or its value cannot be parsed, 5 seconds applies. A version that knows only minutes does not parse the string and applies its own default, 5 minutes; a time chosen in it is written as a number, wins by S2 and applies on all devices as minutes. A version of the app that does not know this entity or field keeps its fields and passes them on, but does not apply them: a version before #255 shows "Inbox" and takes the default list from its own setting on the device. Settings are not transferred through CalDAV.
- S33. The outcome "won't do" (R69 in [product.md](product.md)) is the `wont` field next to `done`. When a task is marked, the same moment is written into both fields; the task counts as "won't do" while both fields are set and equal. Completion writes only `done`, reopening clears both fields. The fields merge by S2 separately: if one device completed the task and another, while offline, marked it "won't do", the outcome is decided by the `done` record with the greater timestamp; if both moments fall into the same minute, the task stays "won't do". A version of the app that does not know the `wont` field keeps it and passes it on, and shows the task as completed. Its reopening clears only `done`, and the task is open on all devices; its completing again writes a new moment, which differs from `wont`, and the task is completed on all devices. The exception is completing again in the same minute in which the mark was set: the moments coincide, and the task stays "won't do". Such a version cannot parse a saved filter with the state "won't do" and shows it as a filter without conditions. The storage format number (S14) does not change.
- S4. The order within a list and within a parent is set by the `pos` field — a string such that a third value can be built between any two values. With equal `pos`, the order is decided by the identifier.
- S5. If after a merge the chain of parents forms a cycle, every device breaks it the same way: for the task in the cycle whose `parent` field has the greatest timestamp, the parent counts as empty. The stored fields are not rewritten on merge; the break is written into the field on the next local move of any task, so that the suppressed parent does not "come back to life" after it.
- S6. A task whose list is deleted or unknown is shown in "Inbox".
- S7. The record of a completed repeat gets an identifier computed from the task identifier and the due date of the repeat. Two devices that completed the same repeat while offline create one record, not two.
- S44. Undoing the completion of a repeat (R128 in [product.md](product.md)) is stored on the repeat record, in the `undo` field: the previous `due`, `start`, `remind` and `repeat` of the task, the `due` and `start` that the completion moved it to, and the previous `done` and `wont` of the subtasks closed by the completion. The undo writes ordinary fields with new timestamps: the record has `done` and `wont` cleared, the task gets its previous values back, the subtasks their previous state. So it merges by S2 and reaches the other devices like any edit. Completing the same repeat again returns the same record (S7). A version that does not know the `undo` field keeps it without using it; it receives an undo made by another device as ordinary field edits.

### Remote storage

```
lists/
  vault.json                    {"format":2,"vault":"<uuid>"}
  log/<device>-<number>.jsonl
  log/<device>-<number>.snap   empty file: the device has a snapshot with this number
  snap/<device>-<number>.jsonl  gzip-compressed (S46)
  blobs/<first two characters>/<sha256>
  push/<device>.json        {"v":1,"url":"https://…"}
  blobs/<first two characters>/<HMAC>  content in an encrypted storage (S55)
  backups/<device>/Lists_(…).listsbackup  backups without attachments (S60)
  v1/vault.json                 {"format":3,"vault":"<uuid>"}: the storage was moved (S49)
```

- S8. A `log/…` file is immutable and belongs to one device; the numbers go in a row starting from one. The first line is a header with the version, the device, the number and the count of changes, then one change per line. A file with a wrong number of lines or an unreadable line counts as unfinished: the device does not move past it and repeats the read on the next sync.
- S9. A device remembers, for every other device, the number of the last file it read. Sync: a request for the listing of `log/`, reading the new files, uploading its own changes as a new file. The content of the file is fixed locally before the first upload attempt, so a retry after a failure sends the same bytes under the same number.
- S10. When the log of a device grows to the threshold of S45, the device writes `snap/<device>-<number>.jsonl`: the full state up to and including that number of its log, and a table "device → number of the last file taken into account". After a successful write it puts the marker `<device>-<number>.snap` into `log/`, then deletes its covered log files, its previous snapshot and its previous marker.
- S11. If some device has no file with the next number, and its snapshot is newer than what was read, the snapshot is read. The reader learns about the snapshot from the marker in `log/`; after the merge, the counters of all devices are raised to the values from its table. Merging a snapshot follows S2, so reading it is safe at any moment.
- S45. The threshold for compacting the log is counted in bytes. A device remembers the size of its last snapshot as it lies in the storage, and how many bytes of its log files it has uploaded after it. The snapshot is written at the end of a pass if the log files after the last snapshot weigh more than that snapshot, or if its log files in `log/` number more than 256. While the device has no snapshot, 16 KB is taken as its size. So snapshots take no more bytes than the changes themselves, and a device that has fallen behind reads no more than a snapshot and a log tail of the same size. A device that is up to date with the storage does not read snapshots (S11). Only the writing device makes the decision, so the storage format does not depend on the threshold. Changing the storage, choosing a side (S37) and restoring from a backup (S40) reset both counts.
- S46. Storage format 2: the snapshot is compressed with gzip, and its name is the same as before. The log file stays uncompressed JSONL, with `"v":2` in its header. The reader tells a compressed file by its first bytes and reads files of format 1 and 2. Moving the storage to format 2:
  - A device of the new version, on its first sync with a storage of format 1, rewrites `vault.json` with format 2 and the previous storage identifier. Two devices that do this at the same time write the same bytes.
  - After that, everything it writes is format 2. The files of format 1 stay in the storage and go away when their devices compact their logs. Nothing is rewritten on purpose.
  - A device of the previous version stops sync by S14: on start, after reading `vault.json`, or earlier, when it meets a file of format 2. The snapshot name does not change for this: under a new name the previous version would not see the snapshot and would wait for the missing log file without an error.
  - There is no way back: the previous version cannot read files of format 2.
- S49. The root of the storage is `lists/`. The format number is set by `vault.json` and the file headers (invariants), not by the folder name. Before #294 the root was `lists/v1/`, and such a storage is moved to `lists/`:
  - On the first sync with the storage after the app starts, the device reads `lists/vault.json`. If it is absent, the device reads `lists/v1/vault.json`. If that is absent too, the storage is new: the device writes `lists/vault.json`, and after it `lists/v1/vault.json` with format 3 and the same storage identifier.
  - If `lists/v1/vault.json` exists and `lists/vault.json` does not, the device moves the storage. First it moves each file from `lists/v1/log/`, `snap/`, `push/` and `blobs/<first two characters>/` under the same name into `lists/`: one `MOVE` request per file, without transferring the content. Then it writes `lists/vault.json` with the storage identifier from `lists/v1/vault.json` and the format by S46. Last, it rewrites `lists/v1/vault.json` to format 3 with the same identifier.
  - The move can be interrupted and repeated from any step: while `lists/vault.json` is absent, the next sync starts it again and moves what is left. Two devices moving at the same time do not get in each other's way. A file that another device has already moved is skipped. A file that already exists in `lists/` is replaced: the name of a log file, a snapshot and content determines its bytes (S8, S13), and `push/` is written only by its own device.
  - A device of the previous version started after the move reads `lists/v1/vault.json` with format 3 and stops by S14. That is why the file stays in `lists/v1/` for good: without it the previous version would create a new empty storage there and sync into it without an error.
  - A device of the previous version that was running during the move writes into `lists/v1/` until it restarts. Such files are sent on afterwards. On the first sync after the app starts, a device with the storage in `lists/` requests the listing of `lists/v1/log/`. If there are files there, it moves them and the files from `lists/v1/snap/` and `lists/v1/push/` the same way as during the move. Attachment content that is not in `lists/blobs/` the device looks for in `lists/v1/blobs/` and, if found, moves it into `lists/`.
  - A server that answers `MOVE` with a method refusal (405, 501) gets the file as a copy: read, write under the new name and delete the old one. The device creates the folders on the path to the new name by S43.
  - When the folder of the new name does not exist yet, the server answers `MOVE` with 409 or 404, and SFTPGo with 403 (#304). On such an answer the device creates the folders on the path to the new name by S43 and repeats `MOVE` once. On 403 it first asks whether the folder of the new name exists, and creates folders only if it does not; 403 with the folder in place stays an error.
  - The empty folders `lists/v1/log/`, `snap/`, `push/` and `blobs/…` stay after the move.
- S50. A compressed snapshot carries in the MTIME field of the gzip header the moment the device wrote it, in seconds since 1970-01-01 UTC. The reader of the snapshot does not use this field. With zero in the field, a program that shows the date from the header shows 1 January 1970.
- S12. A device connected to a non-empty storage for the first time reads the logs and snapshots of the others, then uploads its own state. The local data is not erased: this is a merge, and it is also the default choice where the app asks which side to keep (S36). When the storage changes, the numbering of the device's own log continues, and the first sync publishes a snapshot: without it the readers of the new storage would not find the file with number one.
- S13. An attachment is uploaded into `blobs/` by the hash of its content if it is not there, and downloaded on first access (S35) or in the background (S34). Field changes do not wait for attachments. Content whose hash does not match its name is not saved on the device.
- S34. Sync runs in two passes. The first reads and uploads fields (S9–S12) and ends without touching `blobs/`; after it the app shows what has arrived. The second transfers attachment content: it uploads what the storage does not have and downloads what the device does not have. A failure on one file does not stop the others and does not count as a sync failure: the fields are already merged, and the sync status gives the number of attachments waiting for transfer. An attachment waits while its content is not on the device or while the device has not made sure it is in the storage. The second pass does not delay the next first pass; two second passes do not run at the same time. A device that uploaded content sends a push (S19) so that the others fetch it. The app starts the second pass after every successful first pass. This does not apply to CalDAV: there the content goes inside the task object (C5 in [caldav.md](caldav.md)).
- S43. The device itself creates the folders that do not exist yet in a WebDAV storage: `lists/`, `log/`, `snap/`, `push/` and the folder `blobs/<first two characters>/` for each new hash prefix. When the server refuses to write a file because of a missing folder (404 or 409), the device creates the folders on the path to the file and repeats the write once. It does the same when the server answered with a refusal before reading the whole file and closed the connection: in this case the client sees a dropped connection rather than an answer (a Go server does this with a body over 256 KB). Then the device asks whether the folder of the file exists, and creates folders only if it does not; with any other dropped connection the dropped-connection error stays. The administrator of the storage does not need to create folders by hand (#250).
- S35. The device downloads the content of one attachment on request of the app, outside the queue of the second pass and without waiting for it. If the content is not in the storage yet or does not match the hash, the request ends with an error, and the attachment still waits. This does not apply to CalDAV.
- S47. Content is needed while its hash is referenced by an attachment that is not deleted and whose task is not deleted for good (S25). A task in the Trash keeps the content: it is restored together with its attachments. An attachment whose task is still unknown on the device keeps it too. The device deletes content no longer needed from its attachments folder. This is done only over the whole state, like the reconciliation of S42: at the end of a pass that read everything that was in the storage — the second pass (S34) for WebDAV and a folder, the CalDAV run (C30 in [caldav.md](caldav.md)). A device without sync does it on start. What was deleted from an attachment or deleted for good comes back only by a replacement by S38, and then its content may be gone already.
- S48. Content no longer needed by S47 is deleted from the `blobs/` of the storage as well. Any device that saw it as not needed in the second pass deletes it, unless the data has a field `blob/<hash>/gone` with a timestamp greater than the moment the content stopped being needed. That moment is the greatest timestamp of the `deleted` fields of the attachments with this hash and of the `purged` fields of their tasks. Deleting an already deleted file again is not an error. After the deletion the device writes `gone` with a new timestamp: the record goes with the next uploaded log file, that is, later than the deletion itself. A failure between the deletion and the record repeats both steps on the next pass. A refusal of the storage to delete does not interrupt the pass: it is written to the work log as an ERROR line with the source attachments, and the deletion is repeated on the next pass. A device that received the field `blob/<hash>` forgets that the content was in the storage. If it still needs this content — it attached the same file again while offline — the second pass uploads it again. Empty folders `blobs/<first two characters>/` are not deleted.
- S14. A `vault.json` with an unknown format number stops sync with a clear error; local work goes on. Format 4 is an encrypted storage (S54): a version before #342 stops on it and cannot write into it in plain text. Format 1 is known to the version that writes format 2, and that version moves the storage to it (S46). Format 3 in `lists/v1/vault.json` means that the storage has moved to `lists/` (S49): a version before #294 stops on it, and a later version reads `lists/vault.json`. The file is read on the first sync with the storage after the app starts, and once more when a log file or a snapshot could not be read.
- S17. A sync that has nothing to read and nothing to upload costs one request — the listing of `log/`. The listing of `snap/` is requested on the first sync with the storage after the app starts and when the markers do not explain a gap: the device has no next file but has later ones, or nothing is left in `log/` from an already known device. This is how snapshots written by versions without markers are read.

### Storage encryption

A WebDAV storage and a folder are encrypted with a key derived from a passphrase the user makes up; whoever holds the storage cannot read the tasks and cannot plant an edit that the devices would accept. The decision on the key model: the author of the project, 2026-10-17 (#342).

- S54. **Key.** The data is encrypted by a random data key of 32 bytes. It lies in `vault.json`, wrapped with a key derived from the passphrase: Argon2id, 64 MiB, three passes, one thread, a random salt of 16 bytes; the wrapping is XChaCha20-Poly1305 with the associated data `lists vault <storage id>`, so the `vault.json` of another storage does not open here. An encrypted storage is format 4: `{"format":4,"vault":"<uuid>","salt":"…","nonce":"…","key":"…"}` (base64). The format number is the only thing in the file that is readable without the key. A CalDAV storage is not encrypted: other CalDAV clients must be able to read the tasks in it.
- S55. **What is encrypted.** Log files, snapshots, attachment content and the push addresses in `push/` — under the same names, except content: it lies in `blobs/<first two characters>/<HMAC>`, where the HMAC-SHA256 of its SHA-256 is computed with a key derived from the data key, so the storage cannot check whether it holds a known file. The snapshot markers in `log/` stay empty files. A file is encrypted with XChaCha20-Poly1305 in chunks of 64 KiB (the STREAM construction): `LSE1`, a random nonce prefix of 19 bytes, then the chunks, each with its own authentication tag; the nonce of a chunk is the prefix, the chunk number and the last-chunk flag. The associated data of a chunk is the path under which sync reads the file (for content, the path with the SHA-256), so a file moved under another name does not open. Content is encrypted and decrypted as a stream, as in S52: memory does not grow with the file size. The names of log files (device, number), the sizes and the times of files are visible.
- S56. **Turning it on.** Sync settings → "Encrypt the storage", the passphrase twice and a warning that a forgotten passphrase loses the data in the storage. The device syncs: it reads the storage and uploads its changes, then downloads the attachment content it does not have. If some file could not be read, the storage stays as it was and turning encryption on ends with an error. Then the device writes an encrypted snapshot of its state under the next number of its log — every device reads it, and a device without the key stops on it (S14) — and the encrypted attachment content it has, rewrites the addresses in `push/` encrypted, writes `vault.json` of format 4, and only after that deletes the plain-text files: the logs and snapshots of all devices, the markers and the content. A failure before `vault.json` is written leaves the storage unencrypted, and the device deletes what it wrote for the encrypted one. A deletion interrupted after `vault.json` is written continues on the next sync. A device with the key that opens the encrypted storage for the first time writes a snapshot of its state, checks again which content is in the storage, and rewrites its address in `push/`. So a change that it uploaded in plain text at the moment encryption was turned on still reaches the others, and content that the device turning encryption on did not have is uploaded by whoever has it. A plain-text file in an encrypted storage does not open under the key and stays unread (S57).
- S57. **A file that did not open.** A log file or a snapshot that does not open under the key — changed, moved under another name or written without the key — counts as unreadable (S8): the device does not move past it, and the edit from the storage is not accepted. Content that did not open is not saved on the device, and the attachment waits (S34). A push address that did not open is skipped.
- S58. **The passphrase on other devices.** A device without the passphrase that meets `vault.json` of format 4 stops sync with the error "the storage is encrypted, enter its passphrase"; a wrong passphrase gives its own error. The device learns about the encryption on the first sync after the app starts or when it meets a file that could not be read (S14) — the snapshot of the device that turned encryption on is such a file. Local work goes on. The passphrase field is in the sync settings; a new passphrase applies from the next sync. It is stored where the storage password is: the macOS keychain, Android Keystore, the variable `LISTS_SYNC_PASSPHRASE` for the web server. It does not get into the database or the storage.
- S59. **Changing the passphrase.** A device that has opened the storage rewraps the data key with the new passphrase and a new salt and rewrites only `vault.json`: the other files are not encrypted again. The other devices ask for the new passphrase when they read `vault.json` again: after the app restarts or after the passphrase is changed in their settings. A device that is running while the passphrase is changed goes on syncing: the data key is the same.

### Backups in the storage

Split out of #322, the description is in #347.

- S60. A device puts its backups into a WebDAV storage or a folder: `lists/backups/<device>/Lists_(…).listsbackup`. A backup in the storage is the R87 archive without attachment content: that content already lies in `blobs/`. It is uploaded by a sync pass that ended without an error, when the scheduled time of R88 has passed since the previous backup of this device in the storage; with "Never" (Android) / "Do not create" (macOS) in the schedule and with the R154 setting turned off, backups are not uploaded. After the upload the device deletes its backups in the storage beyond "Keep at most" (R88), oldest first, and does not touch the backups of other devices. A failed upload does not make the pass fail: it is written into the backup status (R154) and the log (R102), and the next pass tries again. With CalDAV there are no backups in the storage.
- S61. In an encrypted storage the backups are sealed with the same key as the other files (S55) and open only with it. When the storage is encrypted (S56), the backups that lay in plain text are deleted together with the other plain-text files; a new backup is uploaded by the next scheduled pass.
- S62. **A storage that is no longer encrypted.** A device that has synced with the storage while it was encrypted does not write into it in plain text: a `vault.json` of another format, or no `vault.json`, stops sync with an error. So the storage cannot silently turn encryption off. If the storage was cleared on purpose, it is connected again: sync is turned off and on again. The app has no way to turn encryption off. A forgotten passphrase loses the data in the storage; the copies on the devices stay, and any of them can connect to a new storage and encrypt it with a new passphrase.

### Which side to keep

A merge by S2 does not ask whose data is more correct. When a device with tasks is connected to a storage with tasks, or when the state of the device differs from the storage on purpose (restoring from a backup), the user chooses one of three: merge, take the data of the storage or send the data of the device. Status: the core is checked by the tests `s36_*`–`s39_*` in `core/tests/sync.rs` and `c28_*` in `core/tests/caldav.rs`. The dialog on Android was checked on 2026-10-09 on an API 36 emulator without a window against the server from `core/examples/webdav.rs`, English interface; the screen was taken from `uiautomator dump`, the data from the app database and from the database of the second device, which was `core/examples/lists.rs`. The storage holds two tasks of the second device, the phone has its own tasks, sync is off: "Save and sync" with a WebDAV address shows a question with three choices, and nothing is written to the storage before the choice. "Use the data of this device…" after confirmation: the second device has the phone's tasks in place and its own two tasks in the Trash; on the phone they are in the Trash as well. Sync is turned off, a task is added on the phone, and one more on the second device; connecting again and "Use the data of the storage…" after confirmation: the phone's task is neither on the phone nor on the second device, the new task of the second device is on the phone, the device identifier has changed, and both have the same number of live tasks. "Cancel" in the question: sync stays off. Not checked on Android: "Merge" in the dialog, cancelling the confirmation, CalDAV, a storage failure during the check, the Russian interface, a real server and a real device. The dialog in the macOS app is built but was not started in use.

- S36. The macOS and Android apps ask when the sync settings are saved with a new or different storage, if there is data on both sides. The device has data when it has a task not in the Trash or a list other than "Inbox". The storage has data when at least one change file lies in `log/` or `snap/`, in `lists/` or, while the storage has not been moved (S49), in `lists/v1/`; for CalDAV — C28 in [caldav.md](caldav.md). The storage check only reads, and uses the address, user name and password from the form. If one of the sides is empty, there is no question and a merge runs: there is nothing to conflict. Changing only the password, ordinary sync starts (S15) and the web server, where the storage is set by environment variables, do not ask the question. Choices: "Merge" — a merge by S12, offered by default; "Use the data of the storage…" (S37); "Use the data of this device…" (S38). The app carries out the last two after a confirmation that says what will be lost. The storage and the chosen side are saved in one action: a sync that was waiting its turn starts with them already and has no time to merge the data before the replacement. Declining the choice does not save the settings. If the storage does not answer during the check, the settings are not saved either, and the app shows an error: without an answer there is no way to know whether there is a choice to make.
- S37. **Take the data of the storage.** The device erases its tasks, lists, filters, shared settings and everything it remembered about the storage, gets a new device identifier and reads the storage as if connected for the first time. Changes it had not uploaded yet are lost. A new identifier is needed because a device does not read its own log files: with the previous one it would not get back what it had uploaded earlier itself. The previous log stays in the storage as the log of a device that will not appear again. Attachment content on disk is not erased and not downloaded again. The settings of the device itself — where to sync, notifications, appearance — stay. With sync through CalDAV the shared settings (S32) stay too: they are not transferred through CalDAV, and there would be nowhere to take them from. Until the first sync has passed, the device is empty.
- S38. **Send the data of this device.** The device remembers the values of all its fields and syncs in the ordinary way, so that it sees everything in the storage and its clock moves past all the timestamps it met (S1). Then, in one write, it gives every remembered field its remembered value with a new timestamp; a field it did not have gets an empty value; a task, list, attachment and filter it did not have get `deleted` and go to the Trash. After that it syncs once more. The other devices get the result by a merge by S2 and do nothing special, so the choice also works with versions of the app that do not know about it. What was only in the storage is not erased but lies in the Trash on all devices: a mistaken replacement can be undone from there. What was deleted for good (S25) in the storage but is live on the device comes back.
- S39. A replacement by S38 survives a failure. If the sync did not pass, the replacement stays pending and completes on the next start by S15. If after the failure the fields of the device are the same as when they were remembered — nothing was accepted from the storage (no network) and nothing was edited on the device — the remembered values are dropped and remembered again on the next attempt, so edits made on the device before it are included in the replacement. An edit made on the device while the sync itself is running is replaced by the remembered value. Changing the storage or turning sync off cancels a pending replacement.

- S40. Restoring from a backup (R90 in [product.md](product.md)) makes the device new to the storage: it gets a new identifier, forgets everything it remembered about the storage, and marks all fields for upload, as when the storage changes (S12). The previous identifier does not fit: the backup could have been restored on another device, and then two devices would write files under one name, and on the same device the log file numbers from the backup are already taken in the storage. If sync is on, the app asks before restoring what to do with the storage: "Merge" — the restored state merges with the storage by S2, and later edits from the storage win, so what was deleted after the backup was made stays deleted; "Replace the data of the storage" — the storage and all devices get the restored state (S38). There is no "Use the data of the storage…" choice here: it would cancel the restore itself. The restore and the choice are carried out in one action, so sync has no time to merge the data before the replacement. With sync off there is no question.

### When it starts

- S15. After a local edit — after two seconds of quiet; on Android this start is handed to the system, so it takes place even if the app is closed by then, and without a network it waits until the network appears. When the app comes to the foreground. While the app is active — once a minute. On Android, in addition, as a background task once every 15 minutes when there is a network. On Android also by a gesture: swiping down at the top of a list (R67 in [product.md](product.md)). With sync through a folder, the macOS app and the web server also start it when a file appears in or disappears from the `log/` of that folder: this is how edits that another program (Syncthing, iCloud Drive) brought into the folder get through.
- S16. A network failure does not lose data: unsynced changes stay locally and go out on the next attempt.

- S18. A device to which the app has assigned a receive address publishes it in `push/<device>.json`. The file is rewritten when the address changes and removed when receiving is turned off. The address is only `http://` or `https://`.
- S19. After a sync pass (S34) that uploaded changes or attachments, the device reads `push/` and sends a `POST` with the body `sync` to each address of the other devices; an address recorded by several devices (S41) gets one request. The requests go out at the same time and only after the pass: the pass does not wait for them, and the next one may start while they are under way. A request carries the sender's identifier in the `X-Title` header. An app that the system may stop right after a background sync (Android) waits for the sending to end before it tells the system that the work is done. A sync that has nothing to upload sends nothing and reads `push/` only to reconcile the topic (S41).
- S20. Delivery of a push is not guaranteed: an error or silence from the recipient does not affect the result of the sync, and the wait for an answer is limited to five seconds. The runs under S15 remain.
- S21. On receiving a push, the app starts an ordinary sync. It uploads nothing, so there is no push in reply.
- S22. The macOS app and the web server receive pushes through an [ntfy](https://ntfy.sh) server, public or one's own: its address is set in the settings. The device picks a random topic of 32 hexadecimal characters once, publishes `<server>/<topic>` as its receive address and, while it runs, keeps a subscription to that topic; it then shares the topic with the other devices of the storage (S41). On a server without sign-in the topic name is the only protection; the server sees the moments of changes, but not the data.
- S41. Devices of one storage that receive pushes under S22 through the same server listen on one topic, and a push reaches them with one request. A device learns the topic from the addresses published in the storage. An address of the form `<its server>/<32 hexadecimal characters>` is a topic on its server. Of such addresses and its own, the device takes the smallest in string order, makes its topic its own and publishes that address (S18). The reconciliation runs on the first pass after the push server is set or changed, and on every pass that uploaded changes. Until the devices have converged on one topic, pushes go to the earlier addresses, and none is lost. A device listens on the topic it writes to itself: it skips a message with its own identifier in the header (S19). Two kinds keep their own addresses: Android, whose address the distributor gives (S24), and a device with another server. A device of an earlier version does not change its topic, but the others may take it; its push arrives in the shared topic as many times as there are devices that published it, and the extra ones cause a pass that has nothing to do.
- S23. A subscription that breaks after it was established counts as a push: a message may have gone by during the break. A failed attempt to connect is repeated no more often than once in ten seconds.
- S24. The Android app receives pushes through [UnifiedPush](https://unifiedpush.org): the connection to the server is held by a distributor app installed on the device (for example, ntfy), which also gives the receive address. Receiving is turned on in the sync settings; without a distributor it cannot be turned on, and the app says so. On receiving a push, the app schedules sync as an expedited system job, so it runs even when the app is closed. The background sync every 15 minutes remains.
- S27. To an ntfy server that requires sign-in, the device presents an access token in the header `Authorization: Bearer <token>`. The token is set in the sync settings next to the address of the push server, and for the web server by the variable `LISTS_PUSH_TOKEN`. The app keeps it where it keeps the storage password; it does not go into the database or the storage. An ntfy user name and password are not accepted. Without a token, requests go as before, without credentials. The token field is hidden behind the switch "The push server requires sign-in"; it is off until a token is set, and saving with the switch off erases the token.
- S28. The token goes only to the device's own server: in the subscription (S22) and in a push (S19) to an address whose scheme, host and port are the same as those of the push server in the settings; the path is not compared. To other addresses a push goes without credentials, and the token does not follow a redirect. This way the token does not reach a server the user did not name, whatever addresses lie in the storage.
- S29. In the Android app, receiving is done by the distributor under its own account, and it does not need the token. For sending, the address of an ntfy server and a token are set in the sync settings; they do not affect receiving under S24. Both fields are hidden behind the switch "ntfy server that requires sign-in": it is off until a server is set, and saving with the switch off erases both the server and the token. A public server without sign-in does not need these fields.
- S30. A refusal of sign-in by the server is visible to the user. If the subscription or a push to the device's own server got the answer 401 or 403, the sync settings show that the push server rejected the token or requires one, and the web server writes this to its log. Retries follow S23; the message is removed when the same request goes through or the settings change. Other push failures are still not shown (S20).
- S31. Background work on Android depends on the system: a phone that restricts the app puts off both scheduled sync and sync on a push. The time allowance for expedited jobs (S24) also depends on how often the app is used; an app exempted from battery optimisation is not subject to these restrictions. So the sync settings show the row "Background work": restricted or unrestricted. A tap on the restricted row opens the system request to exempt Lists from battery optimisation; a tap on the unrestricted row opens the system list where the exemption can be removed. The app shows the same request by itself once: on the first save with sync turned on, on turning on push receiving, or on opening the app when sync is already on, so that someone who set up sync before the request existed sees it too. The user's answer is not remembered; only the fact that the request was shown is remembered. Under the row is a hint: the distributor app needs the same, and on some phones both also need autostart allowed.

- S42. The rule on subtasks (R10 and R112 in `product.md`) is an exception to "merging does not rewrite stored fields" (S5). A device brings the data in line with the rule by ordinary changes with new stamps: it writes empty values into the fields of subtasks, marks their attachments as deleted, and gives a subtask of a subtask the parent of its former parent as its parent. A subtask is a task that has a parent, and that parent has no `project` flag. The bringing in line is done only over the whole state: at the end of a sync run that read everything in the storage, at startup, after an import and after a restore from a backup. In the middle of a run a task of a project may reach the device before the flag of its project, and its fields would be removed for good; so a run broken off in the middle or one that met an unreadable file brings nothing in line, and neither does the startup after it — a run that reaches the end does it. The writing is deterministic: two devices bringing the same data in line write the same values, and a difference of stamps is settled by S2. The storage format number does not change: a device with an earlier version keeps syncing, and a field it writes to a subtask is removed by a device with the new version.

## Invariants

- Two devices that received the same set of changes in any order show the same data.
- The storage has no file that two devices write, except `lists/vault.json`, which is created once and rewritten on the move to format 2 (S46), on encryption (S56) and on a change of the passphrase (S59); the addresses in `push/`, which the device that turned on encryption rewrites encrypted (S56); `lists/v1/vault.json`, rewritten to format 3 on the move (S49); and the contents of `blobs/`, where the name determines the content. The move under S49 moves other devices' files but does not change their bytes.
- The file format is versioned by a number in `vault.json` and in the header of each file.

## Known limitations

- A device whose clock has run far ahead wins conflicts over the same field until the others see its stamps and advance their clocks.
- Rows of deleted records stay in the database and in snapshots. The content of attachments is deleted (S47, S48), but the records about it and the `gone` field stay.
- Until the device that deleted the content and the one that attached it again while offline have exchanged logs, the content is not in the storage, and a third device waits for it (S48).
- The log of a device that will never appear again stays in the storage until it is deleted by hand.
- Replacing the data of the storage with the data of a device (S38) acts on what the device has seen. A change that another device made earlier but uploaded after the replacement is merged under S2: an edit of a field loses to the new stamp, and a task created offline appears on all devices. A log file that could not be read at the moment of the replacement (S8) counts as late in the same way.
- After a replacement under S38 the storage keeps rows of everything that went to the trash, and the state of the device is written anew in full: the log grows by the size of the full state.
- The content of a CalDAV storage is not encrypted (S54). In an encrypted storage the names of the log files, their sizes and times are visible.
- A log file that a device without the key uploaded in plain text after encryption was turned on stays unread (S57) until that device gets the passphrase and writes a snapshot. While it lies there, runs do not count as having read the whole storage, and the bringing in line under S42 and the deletion of unneeded content under S47 wait.
- A device connected to a storage for the first time trusts its `vault.json`: a storage swapped for this device before the first sync can be open (S60 protects only devices that have already seen encryption).
- The push receive address lies in the storage in the open, and devices send a `POST` to any address from there. Whoever can write to the storage can make them contact an arbitrary address; such a request carries no data.
- A push reaches an ntfy server that requires sign-in only from devices that have this same server set in their settings: the sender has no token for another server (S28). Sign-in by user name and password is not supported.
- The entry in `push/` of a device that will never appear again stays until it is deleted by hand; pushes to it go nowhere.
- The content of an attachment that a device of an earlier version uploaded to `lists/v1/blobs/` after the move lies there until a device of the new version asks for it (S49). Unneeded content is deleted under S48 only from `lists/blobs/`.
- A device with a version without marks (before S17) that has never met a reader and has compacted its whole log is seen by the reader after a restart of the app or after the next edit on that device.
