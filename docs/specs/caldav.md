# Lists: синхронизация через CalDAV

Состояние: реализовано в ядре и проверено тестами `core/tests/caldav.rs` против тестового сервера; из настоящих серверов сценарий `real_server_round_trip` из того же файла пройден на Radicale 3.8.2 (2026-10-06); с Nextcloud и другими не запускалось. Источники: решение автора проекта от 2026-10-05 («вторым транспортом»), проверка серверов и клиентов в [architecture.md](../architecture.md), RFC 4791, RFC 5545, RFC 6578.

## Назначение и границы

Второй способ синхронизации, рядом с журналом поверх WebDAV ([sync.md](sync.md)). Устройство пользуется одним из них. CalDAV нужен там, где есть только он, и там, где задачи хочется видеть в других клиентах.

Правила слияния те же: регистр на поле, побеждает бо́льшая метка (S1–S7 из sync.md). Меняется только то, где лежат данные и как обнаруживаются чужие правки.

Не входит: совместные календари с разными правами, приглашения, VEVENT, управляемые вложения (RFC 8607), импорт чужих вложений.

## Требования

### Соответствие

- C1. Список — календарь с поддержкой VTODO. Название и цвет списка лежат в стандартных свойствах `displayname` и `calendar-color`, остальные настройки — в собственном свойстве коллекции. Если сервер собственное свойство не хранит, эти настройки остаются на устройстве и не синхронизируются.
- C2. Задача — один VTODO; `UID` равен идентификатору задачи. Подзадача лежит в календаре своего верхнего предка и ссылается на родителя через `RELATED-TO`.
- C3. В стандартные свойства пишутся название, заметка, начало, срок, приоритет, теги, повтор и выполнение (`SUMMARY`, `DESCRIPTION`, `DTSTART`, `DUE`, `PRIORITY`, `CATEGORIES`, `RRULE`, `STATUS` с `COMPLETED`). Даты пишутся без часового пояса.
- C4. Полное состояние задачи — все регистры с метками, включая поля без стандартного аналога и записи о вложениях — лежит в свойстве `X-LISTS-STATE`.
- C5. Вложение до 5 МБ пишется в VTODO как `ATTACH` в base64 с параметром, несущим его SHA-256. Более крупное остаётся на устройстве; запись о нём синхронизируется.
- C6. Задача в корзине на сервере не хранится: объект удаляется. Восстановление из корзины создаёт его заново. Так же удаляются объекты задач и записей о повторах, убранных очисткой «Выполненных» (R46).

### Чужие клиенты

- C7. Чужие свойства и компоненты объекта сохраняются при каждой записи: приложение меняет только свойства из C3–C5.
- C8. Если стандартное свойство расходится с тем, что записано в `X-LISTS-STATE`, это правка чужого клиента: она принимается как новое значение поля.
- C9. Объект без `X-LISTS-STATE` принимается как задача, собранная из стандартных свойств. Если состояние вырезал чужой клиент, поля без стандартного аналога берутся из базы устройства и возвращаются на сервер.
- C10. Задача, созданная чужим клиентом, получает идентификатор из своего `UID`; чужой календарь — идентификатор, вычисленный из его адреса, одинаковый на всех устройствах.
- C11. Чужой клиент отметил выполненной повторяющуюся задачу — она переходит к следующему повтору по правилам R17, а не закрывается.
- C12. `RRULE`, который не выражается правилами R14–R16, не трогается и не заменяет повтор, записанный в состоянии.

### Обмен

- C13. Запись существующего объекта идёт с `If-Match`, нового — с `If-None-Match: *`. Отказ сервера означает, что объект изменился: он читается заново, сливается, и запись повторяется.
- C14. Объект, исчезнувший с сервера, отправляет задачу в корзину на устройстве. Правка, сделанная на устройстве до этого, остаётся в задаче и видна после восстановления.
- C15. Список удаляется вместе с календарём, только когда в календаре не осталось объектов.
- C16. Повторная синхронизация без правок ничего не пишет на сервер.

### Толчок

- C22. Адреса приёма толчков (S18–S21 из sync.md) лежат в собственном свойстве календаря «Входящие»: таблица «устройство → адрес». Устройство дописывает или убирает свою строку, чужие не трогает. Если сервер свойство не хранит, толчков нет, синхронизация идёт по расписанию.

### Цена прогона

Прогон, которому нечего передать, стоит одного запроса там, где сервер это позволяет. Каждое из правил ниже имеет запасной путь, поэтому сервер без нужной возможности синхронизируется так же, только дороже.

- C18. Адрес коллекции календарей запоминается после первого удачного прогона и выясняется заново, только когда коллекции по нему больше нет. Смена настроек синхронизации его сбрасывает.
- C19. Календарь, чья метка изменений (`getctag`, а без неё `sync-token`) та же, что при последнем полностью прочитанном списке его объектов, не читается. Сервер без таких меток отдаёт список объектов при каждом прогоне. Запись самого устройства тоже меняет метку, поэтому после неё календарь читается ещё раз.
- C20. Изменившийся календарь читается отчётом `sync-collection` (RFC 6578) от метки синхронизации, запомненной при прошлом чтении: сервер называет только изменившиеся и исчезнувшие объекты. Если сервер отчёта не знает, метку не принимает или ответ неполон, читается полный список объектов с ETag.
- C21. Изменившиеся объекты одного календаря, когда их больше одного, читаются отчётом `calendar-multiget` пачками по 20. Объект, которого в ответе нет, и любой объект на сервере без этого отчёта читается отдельным `GET`.
- C17. Задача, у которой с последней сверки не менялись ни регистры, ни объект на сервере, заново не собирается и её вложения не читаются. Сверка — это запись объекта либо вывод, что записывать нечего.

## Известные ограничения

- Серверы, которые вырезают неизвестные `X-`-свойства (проверка указывает на Cyrus), сводят синхронизацию к стандартным полям: порядок задач, напоминания и отсчёт повтора от даты выполнения между устройствами не переносятся.
- Вложение передаётся заново при каждой записи задачи.
- Корзина не общая: задача, удалённая на одном устройстве, попадает в корзину и на остальных, но очистка корзины у каждого своя. По той же причине очищенное из «Выполненных» на одном устройстве на остальных оказывается в корзине, а не исчезает.

## Проверочные сценарии

Тесты — `core/tests/caldav.rs`, сервер — `core/tests/common/dav.rs`. Тест `real_server_round_trip` повторяет обмен на настоящем сервере; он запускается вручную, адрес берёт из `LISTS_CALDAV_URL`.

- C2–C4: задача с подзадачей, сроком, приоритетом, тегами и повтором → на сервере два VTODO со стандартными свойствами и состоянием → второе устройство получает те же задачи.
- S2 через CalDAV: два устройства меняют разные поля одной задачи → у обоих обе правки.
- C7: в объект добавлено чужое свойство `X-OTHER` → после правки задачи на устройстве свойство на месте.
- C8: чужой клиент меняет `SUMMARY` и `DUE` → устройство принимает оба значения, остальные поля не тронуты.
- C9: чужой клиент убирает `X-LISTS-STATE` → после синхронизации состояние снова на сервере, поля без стандартного аналога целы.
- C10: VTODO без состояния, созданный чужим клиентом → задача появляется на обоих устройствах под одним идентификатором.
- C11: чужой клиент ставит `STATUS:COMPLETED` повторяющейся задаче → срок сдвинут, задача открыта.
- C13: два устройства меняют одну задачу до синхронизации → второе получает отказ, сливает и записывает; у обоих итог одинаков.
- C6, C14: удаление на устройстве убирает объект; исчезновение объекта на сервере отправляет задачу в корзину на втором устройстве.
- C6, R46: очистка «Выполненных» на устройстве убирает объекты выполненной задачи, её подзадачи и записи о повторе; на втором устройстве они оказываются в корзине, обратно на сервер не возвращаются.
- C5: вложение доходит до второго устройства с тем же хешем.
- C16: вторая синхронизация подряд не делает ни одной записи.
- C18: адрес найден через `calendar-home-set` → следующие прогоны его не спрашивают; коллекция переехала → адрес находится заново, данные те же.
- C19: прогон без правок — один запрос; правка чужим клиентом в одном календаре → читается только он, задачи остальных календарей остаются на месте; сервер без меток → список каждого календаря при каждом прогоне, итог тот же.
- C20: правка и удаление чужим клиентом доходят через `sync-collection` без полного списка; метка, которую сервер забыл, → полный список, итог тот же.
- C21: первое чтение календаря с несколькими задачами — один `calendar-multiget` и ни одного `GET`; сервер без отчётов → по `GET` на объект, итог тот же.
- C22 (в `core/tests/push.rs`): то же, что S18–S20, через CalDAV; сервер без собственных свойств → толчков нет, свойство не переписывается при каждом прогоне.
- C17: синхронизация без правок не собирает ни одной задачи; правка одной задачи на устройстве или чужим клиентом собирает только её; подзадача переезжает в другой календарь вслед за родителем.
