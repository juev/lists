# Lists: синхронизация через CalDAV

Состояние: реализовано в ядре и проверено тестами `core/tests/caldav.rs` против тестового сервера; из настоящих серверов сценарии `real_server_round_trip` и `real_server_calendar_kept_for_a_deleted_list` из того же файла пройдены на Radicale 3.8.2 (2026-10-06); с Nextcloud и другими не запускалось. Источники: решение автора проекта от 2026-10-05 («вторым транспортом»), проверка серверов и клиентов в [architecture.md](../architecture.md), RFC 4791, RFC 5545, RFC 6578.

## Назначение и границы

Второй способ синхронизации, рядом с журналом поверх WebDAV ([sync.md](sync.md)). Устройство пользуется одним из них. CalDAV нужен там, где есть только он, и там, где задачи хочется видеть в других клиентах.

Правила слияния те же: регистр на поле, побеждает бо́льшая метка (S1–S7 из sync.md). Меняется только то, где лежат данные и как обнаруживаются чужие правки.

Не входит: совместные календари с разными правами, приглашения, VEVENT, управляемые вложения (RFC 8607), импорт чужих вложений.

## Требования

### Соответствие

- C1. Список — календарь с поддержкой VTODO. Название и цвет списка лежат в стандартных свойствах `displayname` и `calendar-color`, остальные настройки — в собственном свойстве коллекции. Если сервер собственное свойство не хранит, эти настройки остаются на устройстве и не синхронизируются.
- C2. Задача — один VTODO; `UID` равен идентификатору задачи. Подзадача лежит в календаре своего верхнего предка и ссылается на родителя через `RELATED-TO`.
- C3. В стандартные свойства пишутся название, заметка, начало, срок, приоритет, теги, повтор и выполнение (`SUMMARY`, `DESCRIPTION`, `DTSTART`, `DUE`, `PRIORITY`, `CATEGORIES`, `RRULE`, `STATUS` с `COMPLETED`; исход «не буду делать» — C27). Даты пишутся без часового пояса.
- C4. Полное состояние задачи — все регистры с метками, включая поля без стандартного аналога и записи о вложениях — лежит в свойстве `X-LISTS-STATE`.
- C5. Вложение до 5 МБ пишется в VTODO как `ATTACH` в base64 с параметром, несущим его SHA-256. Более крупное остаётся на устройстве; запись о нём синхронизируется. Вложения одной задачи занимают в объекте не больше 20 МБ в сумме: они добавляются в порядке хешей, и то, что не поместилось, тоже остаётся на устройстве с синхронизируемой записью. Порядок один на всех устройствах, поэтому они не переписывают объект друг за другом.
- C6. Задача в корзине на сервере не хранится: объект удаляется. Восстановление из корзины создаёт его заново. Так же удаляются объекты задач и записей о повторах, убранных очисткой «Выполненных» (R46).

### Чужие клиенты

- C7. Чужие свойства и компоненты объекта сохраняются при каждой записи: приложение меняет только свойства из C3–C5.
- C8. Если стандартное свойство расходится с тем, что записано в `X-LISTS-STATE`, это правка чужого клиента: она принимается как новое значение поля.
- C9. Объект без `X-LISTS-STATE` принимается как задача, собранная из стандартных свойств. Если состояние вырезал чужой клиент, поля без стандартного аналога берутся из базы устройства и возвращаются на сервер.
- C10. Задача, созданная чужим клиентом, получает идентификатор из своего `UID`; чужой календарь — идентификатор, вычисленный из его адреса, одинаковый на всех устройствах.
- C11. Чужой клиент отметил выполненной повторяющуюся задачу — она переходит к следующему повтору по правилам R17, а не закрывается.
- C27. Задача «не буду делать» (R69) пишется со `STATUS:CANCELLED` и без `PERCENT-COMPLETE`; свойство `COMPLETED` с моментом закрытия остаётся, чтобы версия приложения, которая исхода не знает, читала задачу закрытой, а не возвращала её в работу. Чужой клиент поставил `STATUS:CANCELLED` открытой задаче — она получает исход «не буду делать» по правилам R69: повторяющаяся переходит к следующему повтору, как в C11. Чужой клиент сменил `CANCELLED` на `COMPLETED` или обратно — меняется исход, момент закрытия остаётся; вернул `NEEDS-ACTION` — задача возвращается в работу. Объект со `STATUS:COMPLETED`, в котором `COMPLETED` совпадает с моментом закрытия задачи «не буду делать», записан версией, не знающей исхода: исход не меняется.
- C12. `RRULE`, который не выражается правилами R14–R16, не трогается и не заменяет повтор, записанный в состоянии.

### Обмен

- C13. Запись существующего объекта идёт с `If-Match`, нового — с `If-None-Match: *`. Отказ сервера означает, что объект изменился: он читается заново, сливается, и запись повторяется.
- C14. Объект, исчезнувший с сервера, отправляет задачу в корзину на устройстве. Правка, сделанная на устройстве до этого, остаётся в задаче и видна после восстановления.
- C15. Список, удалённый на одном устройстве, удаляется и на остальных: удаление записывается в состояние календаря (C1). Сам календарь удаляется с сервера, только когда в нём не осталось объектов; до тех пор он остаётся ради объектов чужих клиентов, а списком ни на одном устройстве не показывается.
- C16. Повторная синхронизация без правок ничего не пишет на сервер.
- C23. Объект читается целиком, если он не больше 32 МБ. Более крупный объект и объект, который не разбирается как iCalendar, в задачу не превращается и не перезаписывается; остальное синхронизируется как обычно, а состояние синхронизации показывает ошибку с адресом объекта. Пока ETag объекта тот же, заново он не читается, и ошибка остаётся после каждого прогона. Объект, который изменился и прочитался, принимается как обычно.
- C24. Календарь, пропавший по известному адресу, означает удаление списка, только если у списка не нашлось календаря по другому адресу. Календарь с тем же идентификатором списка в последнем сегменте адреса — тот же календарь после переезда: список, его настройки и задачи остаются на месте, с сервера ничего не удаляется.

### Проверка настроек

- C26. Проверка настроек до сохранения (S26 из sync.md) находит коллекцию календарей тем же путём, что первый прогон (C18), и читает список календарей в ней. Найденный адрес не запоминается, календари не создаются. Коллекция нашлась — подключение есть, даже если календарей в ней пока нет; коллекции нет — адрес не найден; отказ сервера и сбой сети сообщаются как при синхронизации.

### Толчок

- C22. Адреса приёма толчков (S18–S21 из sync.md) лежат в собственном свойстве календаря «Входящие»: таблица «устройство → адрес». Устройство дописывает или убирает свою строку, чужие не трогает. Если сервер свойство не хранит, толчков нет, синхронизация идёт по расписанию.

### Цена прогона

Прогон, которому нечего передать, стоит одного запроса там, где сервер это позволяет. Каждое из правил ниже имеет запасной путь, поэтому сервер без нужной возможности синхронизируется так же, только дороже.

- C18. Адрес коллекции календарей запоминается после первого удачного прогона и выясняется заново, только когда коллекции по нему больше нет. Смена настроек синхронизации его сбрасывает.
- C19. Календарь, чья метка изменений (`getctag`, а без неё `sync-token`) та же, что при последнем полностью прочитанном списке его объектов, не читается. Сервер без таких меток отдаёт список объектов при каждом прогоне. Запись самого устройства тоже меняет метку, поэтому после неё календарь читается ещё раз. То же относится к календарю удалённого списка, который остаётся на сервере из-за чужих объектов (C15): пока его метка та же, что была, когда в нём нашлись объекты, он не читается и на пустоту не проверяется. На сервере без меток такой календарь перечисляется один раз за прогон.
- C20. Изменившийся календарь читается отчётом `sync-collection` (RFC 6578) от метки синхронизации, запомненной при прошлом чтении: сервер называет только изменившиеся и исчезнувшие объекты. Если сервер отчёта не знает, метку не принимает или ответ неполон, читается полный список объектов с ETag.
- C21. Изменившиеся объекты одного календаря, когда их больше одного, читаются отчётом `calendar-multiget` пачками по 20. Объект, которого в ответе нет, и любой объект на сервере без этого отчёта читается отдельным `GET`.
- C25. Объект, который не является задачей приложения — событие чужого клиента или VTODO без пригодного `UID`, — запоминается по ETag и заново не читается, пока ETag тот же. Задачей он не становится и на сервере не меняется. Объект без ETag запомнить нечем: он читается при каждом чтении календаря.
- C17. Задача, у которой с последней сверки не менялись ни регистры, ни объект на сервере, заново не собирается и её вложения не читаются. Сверка — это запись объекта либо вывод, что записывать нечего.

## Известные ограничения

- Серверы, которые вырезают неизвестные `X-`-свойства (проверка указывает на Cyrus), сводят синхронизацию к стандартным полям: порядок задач, напоминания и отсчёт повтора от даты выполнения между устройствами не переносятся.
- Вложение передаётся заново при каждой записи задачи.
- Проверка настроек (C26) не отличает сервер WebDAV без CalDAV от пустой коллекции календарей: в обоих случаях коллекция отвечает и календарей в ней нет. Разница выясняется при первой синхронизации, когда сервер отказывается создать календарь.
- Вложения, которые не поместились в объект (C5), есть только на устройствах, где они уже лежат: на остальные приходит запись без содержимого. Чужие вложения в объекте в лимит не входят, поэтому вместе с ними объект может превысить 32 МБ и перестать читаться (C23).
- Объект больше 32 МБ, записанный приложением до появления лимита, не уменьшается сам: он перезаписывается при следующей правке задачи на устройстве, которое его записало.
- Собственные ограничения серверов на размер объекта не проверялись: сервер с порогом ниже 28 МБ откажет в записи, и это будет ошибкой прогона.
- Сервер, который не хранит собственное свойство коллекции (C1), не передаёт и удаление списка, пока календарь не пуст: на остальных устройствах список остаётся пустым, пока календарь не исчезнет.
- Общие настройки приложения (S32 в [sync.md](sync.md)) через CalDAV не передаются: время, которое выполненная задача остаётся в представлении (R68 в [product.md](product.md)), задаётся на каждом устройстве.
- Чужой календарь после переезда становится новым списком: его идентификатор вычислен из полного адреса (C10), поэтому переезд неотличим от удаления одного календаря и появления другого. Задачи переходят в новый список с тем же названием, прежний удаляется.
- Корзина не общая: задача, удалённая на одном устройстве, попадает в корзину и на остальных, но очистка корзины у каждого своя. По той же причине очищенное из «Выполненных» на одном устройстве на остальных оказывается в корзине, а не исчезает.

## Проверочные сценарии

Тесты — `core/tests/caldav.rs`, сервер — `core/tests/common/dav.rs`. Тесты `real_server_round_trip` и `real_server_calendar_kept_for_a_deleted_list` повторяют обмен на настоящем сервере; они запускаются вручную, адрес берут из `LISTS_CALDAV_URL`. Второй играет чужого клиента через `curl`; цену прогона показывает журнал запросов самого сервера.

- C2–C4: задача с подзадачей, сроком, приоритетом, тегами и повтором → на сервере два VTODO со стандартными свойствами и состоянием → второе устройство получает те же задачи.
- S2 через CalDAV: два устройства меняют разные поля одной задачи → у обоих обе правки.
- C7: в объект добавлено чужое свойство `X-OTHER` → после правки задачи на устройстве свойство на месте.
- C8: чужой клиент меняет `SUMMARY` и `DUE` → устройство принимает оба значения, остальные поля не тронуты.
- C9: чужой клиент убирает `X-LISTS-STATE` → после синхронизации состояние снова на сервере, поля без стандартного аналога целы.
- C10: VTODO без состояния, созданный чужим клиентом → задача появляется на обоих устройствах под одним идентификатором.
- C11: чужой клиент ставит `STATUS:COMPLETED` повторяющейся задаче → срок сдвинут, задача открыта.
- C27: задача «не буду делать» → в объекте `STATUS:CANCELLED` и `COMPLETED`, свойства `PERCENT-COMPLETE` нет; второе устройство получает её с тем же исходом. Чужой клиент ставит `STATUS:CANCELLED` открытой задаче → у устройства она «не буду делать»; повторяющейся → срок сдвинут, задача открыта, в журнале запись «не буду делать»; меняет `CANCELLED` на `NEEDS-ACTION` → задача открыта; меняет `CANCELLED` на `COMPLETED` с новым временем → задача выполнена; ставит `STATUS:COMPLETED`, не трогая `COMPLETED` → задача остаётся «не буду делать».
- C13: два устройства меняют одну задачу до синхронизации → второе получает отказ, сливает и записывает; у обоих итог одинаков.
- C6, C14: удаление на устройстве убирает объект; исчезновение объекта на сервере отправляет задачу в корзину на втором устройстве.
- C6, R46: очистка «Выполненных» на устройстве убирает объекты выполненной задачи, её подзадачи и записи о повторе; на втором устройстве они оказываются в корзине, обратно на сервер не возвращаются.
- C5: вложение доходит до второго устройства с тем же хешем.
- C5: четыре вложения по 5 МБ доходят все; из семи по 4,9 МБ в объекте четыре, задача и все семь записей приходят на второе устройство, ни одно из устройств объект повторно не пишет, правка на втором устройстве оставляет в объекте те же четыре.
- C23: чужой объект в 33 МБ → ошибка с его адресом, остальные задачи календаря приходят, следующий прогон объект не читает, ошибка в состоянии остаётся, свои правки уходят на сервер; объект уменьшен → он становится задачей, ошибки нет.
- C23: объект известной задачи вырос до 33 МБ, задача изменена на устройстве → объект не перезаписан; объект уменьшен → обе правки сходятся.
- C16: вторая синхронизация подряд не делает ни одной записи.
- C18: адрес найден через `calendar-home-set` → следующие прогоны его не спрашивают; коллекция переехала → адрес находится заново, данные те же.
- C24: коллекция календарей переехала → на обоих устройствах список с настройками и задачей на месте, во «Входящих» пусто, объект лежит в календаре по новому адресу, следующий прогон ничего не пишет; чужой календарь после переезда → один список с тем же названием и той же задачей.
- C19: прогон без правок — один запрос; правка чужим клиентом в одном календаре → читается только он, задачи остальных календарей остаются на месте; сервер без меток → список каждого календаря при каждом прогоне, итог тот же.
- C15: список удалён на одном устройстве, в его календаре осталось чужое событие → списка нет на обоих устройствах, его задача в корзине, календарь на месте, прогон без правок на втором устройстве — один запрос; событие убрано чужим клиентом → календарь удаляет то устройство, которое синхронизируется первым.
- C15, C19: список удалён, в его календаре осталось чужое событие → календарь на месте, прогон без правок — один запрос, в том числе после выключения и включения синхронизации; сервер без меток → один список этого календаря за прогон; событие убрано чужим клиентом → календарь удалён.
- C25: сервер без меток, в календаре списка два чужих события → прогон без правок не делает ни одного `GET`; событие изменено → один `GET`, следующий прогон снова без них, ошибки в состоянии нет; событие исчезло → задачи на месте; по адресу события записана задача → она появляется в списке.
- C20: правка и удаление чужим клиентом доходят через `sync-collection` без полного списка; метка, которую сервер забыл, → полный список, итог тот же.
- C21: первое чтение календаря с несколькими задачами — один `calendar-multiget` и ни одного `GET`; сервер без отчётов → по `GET` на объект, итог тот же.
- C22 (в `core/tests/push.rs`): то же, что S18–S20, через CalDAV; сервер без собственных свойств → толчков нет, свойство не переписывается при каждом прогоне.
- C26: верный пароль → подключение есть, на сервер ушли только `PROPFIND`, календарей не появилось; коллекция названа через `calendar-home-set` → подключение есть; неверный пароль → ошибка с 401; коллекции нет → адрес не найден.
- C17: синхронизация без правок не собирает ни одной задачи; правка одной задачи на устройстве или чужим клиентом собирает только её; подзадача переезжает в другой календарь вслед за родителем.
